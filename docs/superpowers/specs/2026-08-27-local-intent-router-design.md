# 本地意图路由与完整提示词生成设计

日期：2026-08-27

## 1. 目标

在不增加 API Key、不联网、不产生服务费用的前提下，把当前基于关键词的 Prompt Router 升级为更稳定的本地意图匹配器，并让用户点击“使用”时得到一段可以直接复制到任意 AI 对话框的完整提示词。

本次版本以当前 12 条中文提示词为范围，目标是让自然表达不再严重依赖某个固定关键词，同时在无法判断时诚实地要求用户确认。

## 2. 非目标

- 不接入 OpenAI、Claude、DeepSeek 或其他远程模型。
- 不在本版本内加入 API Key 设置、账号系统或云端同步。
- 不根据用户没有提供的信息编造事实、目标、约束或背景。
- 不把本地规则包装成“AI 已理解”。

## 3. 方案选择

采用“结构化意图元数据 + 本地证据评分 + 反向排除 + 提示词编译”的方案。

纯关键词方案对自然语言变化不敏感；内置本地模型会显著增加安装包、启动时间和维护成本。结构化规则可以保持完全免费和离线，同时为后续接入可选 AI 保留清晰边界。

## 4. 匹配设计

### 4.1 提示词元数据

每条 Prompt 的路由元数据包含：

- `intent`：这条提示词解决的核心意图，例如 `concept-explanation`、`decision`、`fact-checking`。
- `positiveExamples`：应该命中的自然表达示例。
- `negativeExamples`：看起来相似但不应该命中的表达示例。
- `primaryVariable`：路由问题应该自动填入的主要变量。
- 现有的名称、用途、分类、关键词和变量继续保留，用于搜索和兼容用户编辑的文件。

泛化词如“问题”“方案”“产品”“设计”“决定”只能作为低权重辅助证据，不能单独触发高置信度匹配。

### 4.2 评分原则

本地路由依次处理：

1. 识别用户是在理解、选择、核查、拆解、研究、推导、实验、自我认识还是人生规划。
2. 对候选 Prompt 计算名称、意图短语、正例相似短语、用途和关键词等正向证据。
3. 使用负例和冲突意图扣分，避免“为什么”一律进入双层解释法，也避免“设计”一律进入人生设计术。
4. 根据最高分和与第二名的差距决定状态。

状态规则：

- `matched`：最高分达到高置信度阈值，且没有明显冲突。
- `needsManualChoice`：存在候选但分差不足，展示最多 3 个候选和匹配理由。
- `unavailable`：提示词库为空。

没有任何证据时，不把提示词库开头的三条伪装成匹配结果；界面要明确显示“暂时无法判断”，引导用户搜索或手动选择。

### 4.3 可解释性

每个候选都显示简短理由，例如“识别到：在两个方向之间做决定”“命中概念解释意图”“存在研究对象和横向比较信号”。

不得显示内部权重、规则表达式或“AI 判断”等不准确描述。

## 5. 完整提示词生成与复制

### 5.1 生成规则

路由模式下，用户原始问题自动填入候选 Prompt 的 `primaryVariable`。如果提示词没有变量，则在正文末尾追加“用户原始问题”。

其他未提供的变量统一显示为“（暂未提供）”，不留空白占位符，也不凭空补写内容。

例如用户输入“地球为什么是圆的”，选择“双层解释法”后生成：

```text
我想学习的是：地球为什么是圆的。

请分两层解释：
第一层，小白版……
第二层，专业版……
```

### 5.2 交互

- 路由结果中的按钮改为“生成并复制”。
- 复制前显示完整提示词预览，用户可以确认内容是否正确。
- 提供“复制完整提示词”和“复制原始模板”两个动作。
- 搜索模式没有用户问题时，默认复制原始模板；用户也可以在预览中补充问题。
- 复制成功后保留当前反馈和剪贴板兜底行为；自动粘贴失败时仍重新显示面板。

### 5.3 边界

本功能是本地模板编译，不是 AI 改写。它会把已有问题放进合适位置、处理占位字段和格式，但不会替用户扩写背景或生成事实。

## 6. 数据流

```text
用户问题
  -> 本地文本归一化
  -> 意图证据提取
  -> 正例加分 / 反例扣分 / 冲突检查
  -> 候选与置信度
  -> 用户确认或手动选择
  -> primaryVariable 填充
  -> 未提供字段标记
  -> 完整提示词预览
  -> 复制剪贴板并尝试粘贴
```

## 7. 测试设计

建立固定的 100 题回归集：

- 12 条 Prompt 各覆盖多种自然表达；
- 包含概念解释、购物决策、研究、事实核查、复杂问题、第一性原理、跨领域、实验、自我认识和人生方向等类别；
- 加入容易混淆的反例；
- 加入明确应该保持人工选择的模糊问题。

验收标准：

- 96 个明确问题至少 90 个 Top-1 命中期望 Prompt；
- 4 个模糊问题全部保持 `needsManualChoice`；
- 未提供变量不再输出裸占位符；
- 完整测试套件全部通过；
- 后续每次修改路由规则都自动运行这 100 题。

## 8. 风险与退出条件

最大风险是纯本地规则对从未见过的表达仍然理解有限。因此低置信度时必须允许人工选择，不能为了提高“自动命中率”而强行猜测。

如果加入正例、反例和冲突规则后，100 题明确问题仍无法达到 90/96，说明继续堆规则的收益不足，应暂停扩展规则，重新评估是否需要可选的用户自带 API Key 或本地语义模型。

## 9. 交付顺序

1. 先扩展类型和 Prompt 元数据，保证旧文件仍可读取。
2. 重写本地评分和置信度判断，先用失败测试驱动实现。
3. 抽出统一的提示词生成器，删除渲染逻辑重复实现。
4. 增加完整提示词预览和复制动作。
5. 固化 100 题回归测试，运行全部测试并记录结果。
